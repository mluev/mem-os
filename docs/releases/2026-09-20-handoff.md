## One artifact bundle

The `ci` workflow's wheel job uploads `mem-os-release-candidate-<commit>` for
every passing package build. It contains one archive plus its SHA-256 checksum:
server, standalone CLI, Python SDK, TypeScript SDK, committed source, dependency
lock and hashed requirements, OpenAPI, agent guide, all documentation, and file
checksums. The manifest identifies the exact source commit. CI retains the
download for 90 days; preserve it in release storage if it is used for deployment.
The bundle's manifest describes the combined build. Earlier dated build manifests
remain historical verification records and identify their own source checkpoints.

To reproduce after completing the normal checks and committing source changes:

```sh
uv build --wheel
uv build --project cli --wheel
uv build --project sdk/python --wheel
pnpm --dir sdk/typescript build
pnpm --dir sdk/typescript pack --pack-destination ../../dist
uv export --locked --no-dev --no-emit-project -o dist/requirements.txt
uv run python tools/bundle_release.py
```

Verify the outer checksum, then `SHA256SUMS` inside the extracted bundle. Build
directories must contain exactly one current wheel for each distribution. The
bundler refuses tracked source changes and an existing output directory. Only
committed source is archived; local credentials, models, databases, and stashes
are excluded.

## Release boundary

Combining and publishing the code does not deploy a production service or promote
a ranking policy. Retrieval still returns substantial irrelevant context and
failed the diagnostic's empty-context abstention checks. The synthetic MPS
measurements do not establish sustained capacity on the deployment CPU. Use a
fresh heldout corpus for subsequent ranking changes and rehearse recovery on the
deployment host before opening production traffic.
