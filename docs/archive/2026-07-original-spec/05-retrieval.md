# 05 — Поиск и сборка контекста

Самая сложная часть. Записать факт легко. Достать нужный из десяти тысяч —
нет.

Косинусного сходства недостаточно: оно не знает, что факт устарел, что он
неважный, и что ты уже двадцать раз им не воспользовался.

## Формула

```python
score = (0.55 * similarity
       + 0.20 * importance
       + 0.15 * recency
       + 0.10 * scope_boost)
```

Веса — стартовые. Крутить их **только по эвалу**, не по ощущениям.

### similarity

Косинус из Qdrant, 0..1. Берём top-50, потом пересчитываем — переранжирование
дешёвое, а расширенная выборка спасает от того, что нужный факт был
пятидесятым по косинусу, но первым по важности.

### recency — забывание

```python
recency = exp(-age_days / tau[type])
```

```python
tau = {
    "preference": 540,   # полтора года
    "fact":       900,
    "skill":      270,
    "relation":   270,
    "project":    180,
    "decision":   180,
    "task":         2,   # задачи умирают почти сразу
}
```

`age_days` считается от `updated_at`, **не** от `created_at`. Факт,
подтверждённый вчера, свежий, даже если создан два года назад.

Смысл разных τ: «живёт в Ташкенте» через год всё ещё правда, «сегодня чиню
баг #14» через два дня — мусор.

### scope_boost

```python
0.0  # scope='user'        — общий фон
0.5  # scope='project' и проект совпадает с текущим
1.0  # scope='task'  и задача совпадает с текущей
-∞   # scope='project'/'task', но ключ НЕ совпадает → выбрасываем
```

Факты из чужого проекта не должны просто получать меньший вес — они должны
отфильтровываться на уровне Qdrant, до всякого ранжирования.

## Дедуп на чтении

Даже с ночным консолидатором в выдачу попадут почти-одинаковые факты. Жадный
проход сверху вниз:

```python
kept = []
for m in ranked:
    if all(cos(m.vec, k.vec) < 0.90 for k in kept):
        kept.append(m)
```

Векторы уже есть в памяти после поиска, второй раз считать не надо.

## Порог релевантности

**Делать до всего остального.** Векторный поиск всегда вернёт `k` результатов,
как бы далеко они ни были. Без порога на любой запрос в промпт уедет 20 фактов,
включая полностью посторонние, и модель будет пытаться их учесть.

```python
FLOOR = 0.35                        # калибровать по эвалу
kept = [m for m in kept if m.similarity >= FLOOR]
```

**Пустая выдача — допустимый и правильный ответ.** Это неочевидно: пустая
память лучше случайной. Если ничего не прошло порог, возвращаем `[]`, и агент
работает без блока памяти.

## Сколько отдавать: гибко, а не 800 токенов

Фиксированное число неверно в обе стороны: на «что ты обо мне знаешь» мало,
на «сделай рефактор функции» много. Три механизма вместо константы.

### 1. Обрыв по разрыву (elbow)

Главный. Отдаём естественный кластер релевантного, а не первые N.

```python
def elbow_cut(scored, min_keep=1, max_keep=30):
    if len(scored) <= min_keep:
        return scored
    gaps = [(scored[i].score - scored[i+1].score, i+1)
            for i in range(min_keep - 1, min(len(scored) - 1, max_keep))]
    biggest_gap, idx = max(gaps, key=lambda g: g[0])
    return scored[:idx] if biggest_gap >= 0.08 else scored[:max_keep]
```

Скоры `0.81, 0.78, 0.74, 0.41, 0.39` → отдаём три. Скоры
`0.71, 0.69, 0.68, 0.67, 0.66` → отдаём все, они правда все релевантны.

### 2. Потолок от вызывающего

Только агент знает, сколько у него осталось контекста. Он передаёт `max_tokens`
как **ограничение сверху**, а не как цель. В адаптере:

```python
max_tokens = clamp(int(0.08 * remaining_context_tokens), 200, 2000)
```

К концу длинной сессии контекста мало → потолок падает сам.

### 3. Режим запроса

```python
mode = "auto"      # elbow + порог, дефолт
mode = "profile"   # top-N по importance, игнорируя запрос
mode = "focused"   # только высокий порог, максимум 5 фактов
mode = "off"       # ничего
```

`profile` нужен для деградировавших запросов — см. следующий раздел.
`focused` для узких технических задач, где лишний контекст только мешает.

### Итог

```python
def pack(scored, max_tokens, mode="auto"):
    if mode == "off":
        return []
    if mode == "profile":
        scored = by_importance(limit=12)
    elif mode == "focused":
        scored = [m for m in scored if m.similarity >= 0.55][:5]
    else:
        scored = elbow_cut(scored)

    out, used = [], 0
    for m in scored:
        t = len(m.text) // 3            # грубая оценка для кириллицы
        if used + t > max_tokens:
            break
        out.append(m); used += t
    return out
```

Ориентир по факту: 200–1200 токенов, медиана около 400. Если медиана уползла
к потолку — порог слишком низкий, а не память слишком богатая.

## Бессодержательные запросы

«ага», «продолжай», «а что думаешь?» — эмбеддинг такого указывает в случайную
сторону, и поиск уверенно вернёт что-нибудь постороннее.

```python
def is_degenerate(q: str) -> bool:
    words = [w for w in re.findall(r"\w+", q.lower()) if w not in STOPWORDS]
    return len(q.strip()) < 12 or len(words) < 2
```

На таких запросах переключаемся в `mode="profile"`: стабильный набор
top-importance фактов. Он не относится к запросу, зато он всегда правда —
в отличие от случайных соседей.

## Обратная связь

После выдачи:

```sql
UPDATE memories
   SET last_retrieved_at = ?, retrieval_count = retrieval_count + 1
 WHERE id IN (...);
```

Даёт две вещи:
- ночью понижать importance у фактов, не всплывавших 90 дней;
- видеть, какие факты не достаются никогда — это ошибки экстрактора,
  их надо разбирать руками.

## Эвал — делать в фазе 1, не потом

Без этого ты не сможешь ответить, стало лучше или хуже. Все правки формулы
превратятся в гадание.

**Проверять содержание, а не id.** Реэкстракция создаёт новые id, то есть эвал
по id развалится ровно в тот момент, когда понадобится больше всего — при первой
смене промпта. Совпадение — по эмбеддингу к эталонной формулировке.

Файл `eval/queries.yaml`, 30 строк, пополняется по ходу:

```yaml
- query: "какой фреймворк я использую"
  expect_text: "использует Vue"        # match: cos(emb(факт), emb(эталон)) > 0.75
  reject_text: "использует React"      # не должно попасть в выдачу
  expect_count: [1, 4]                 # сколько фактов ожидаем, диапазон

- query: "где лежит авторизация"
  expect_text: "аутентификация в auth/"
  scope: project
  scope_key: memkit

- query: "ага"                          # деградировавший запрос
  expect_mode: profile
  reject_text: "аутентификация в auth/" # случайный сосед попасть не должен

- query: "какая погода в Ташкенте"      # к памяти отношения не имеет
  expect_count: [0, 0]                  # обязана вернуться пустота
```

Метрики: `recall@k` по `expect_text`, доля нарушений по `reject_text`,
попадание в `expect_count`, медиана `used_tokens`.

Последние два типа кейсов — пустые и деградировавшие запросы — важнее
положительных. Положительные проходят почти всегда; ломается именно
дисциплина молчания.

Прогон — одна команда, до и после каждой правки весов или промпта:

```bash
python -m eval.run --before v3 --after v4
```

30 запросов достаточно. Смысл не в статистической строгости, а в том, чтобы
регресс было видно сразу.

## Порядок оптимизации

Когда качество не устраивает, чинить в таком порядке:

1. **Экстрактор.** Плохие факты нельзя вытащить хорошим поиском. 80% проблем
   здесь.
2. **Фильтры.** Не отсекается ли лишнее по scope и status.
3. **Веса формулы.**
4. **Гибридный поиск** (добавить BM25 в слот `bm25`). Помогает там, где нужен
   точный термин: имена, версии, названия пакетов. Дай эмбеддингу шанс
   провалиться сам, прежде чем это строить.

Типичная ошибка — начать с пункта 4, потому что он самый интересный.
