# 08 — Как это тестировать

У системы нет единственного правильного вывода. Поэтому обычные юнит-тесты
покрывают только сантехнику, а качество проверяется другими средствами.
Четыре слоя, строго в этом порядке.

**Нулевой шаг: наблюдаемость.** Пока ты не можешь одной командой посмотреть,
что лежит в базе, ты тестируешь вслепую. `memkit list --recent 50`,
`memkit show <id>`, `memkit events --tail`. Час работы, без этого дальше нет
смысла.

---

## Слой 1 — Сантехника

Детерминированные тесты, `pytest`, зелёные всегда. Час-два работы. Начинать
с них не потому, что они важнее, а потому что они быстро покажут, что из
доков реально собрано, а что только описано.

```python
def test_reindex_roundtrip():
    before = search("любой запрос")
    reindex()
    assert count_qdrant() == count_sqlite_active()
    assert ids(search("любой запрос")) == ids(before)

def test_idempotent_ingest():
    p = payload(external_id="fixed-1")
    post_message(p); post_message(p)
    assert count_messages(external_id="fixed-1") == 1

def test_soft_delete():
    mid = add_memory("тестовый факт")
    delete_memory(mid)
    assert mid not in ids(search("тестовый факт"))
    assert sqlite_row(mid) is not None
    assert last_event(mid).action == "memory.deleted"

def test_scope_isolation():
    add_memory("аутентификация в auth/", scope="project", scope_key="A")
    res = search("где авторизация", scope_key="B")
    assert res == []

def test_assistant_only_source_rejected():
    ops = apply_ops(source_roles=["assistant"], op="ADD")
    assert ops == []
    assert last_event().action == "memory.rejected"

def test_provider_never_raises():
    stop_service()
    for call in (lambda: prov.prefetch("x"),
                 lambda: prov.sync_turn("u", "a", session_id="s"),
                 lambda: prov.on_session_end()):
        call()          # никаких исключений наружу
    assert prov.prefetch("x") == ""
```

Плюс табличный тест скраба: 20 строк с секретами разных форматов, в каждой
проверяем, что значение не дошло до базы.

**Критерий:** всё зелёное. Если что-то красное — дальше не идти.

## Слой 2 — Извлечение

Здесь ломается чаще всего, и здесь дороже всего ошибки: плохой факт нельзя
вытащить хорошим поиском.

Золотой набор: 40–60 фрагментов диалога с ожидаемым результатом. Совпадение
текста — по эмбеддингу к эталону, не по строке.

```yaml
- name: смена фреймворка
  window:
    - {role: user, text: "да я месяц назад слез с реакта, вью норм заходит"}
  candidates:
    - {id: c1, text: "Пользователь предпочитает React"}
  expect:
    - {op: UPDATE, id: c1, type: preference, text_like: "использует Vue"}

- name: ассистент сказал, не пользователь
  window:
    - {role: user, text: "а что лучше для стейта?"}
    - {role: assistant, text: "Тебе подойдёт Pinia, она проще Vuex"}
  expect: []                    # пользователь ничего не утверждал

- name: секрет в выводе команды
  window:
    - {role: tool, text: "AWS_SECRET_ACCESS_KEY=wJalrXUtn... loaded"}
  expect: []

- name: сиюминутное состояние
  window:
    - {role: user, text: "что-то я сегодня никакой, голова не варит"}
  expect: []

- name: отрицание переводится в утверждение
  window:
    - {role: user, text: "всё, редакс больше не используем"}
  expect:
    - {op: ADD, text_not_like: "не использует"}
```

**Половина набора должна ожидать пустоту.** Это тот тест, который все
пропускают, и именно он ловит отравление памяти. Положительные кейсы проходят
почти всегда — ломается дисциплина молчания.

Метрики: доля точных совпадений по `op`, доля ложных срабатываний на пустых
кейсах (главная), доля неверного `scope`.

Прогонять на каждом изменении промпта, до и после, обе версии рядом.

## Слой 3 — Поиск

Эвал из `05-retrieval.md`, но важно, какие кейсы в нём есть:

| Тип кейса | Что проверяет | Сколько |
|---|---|---|
| прямое попадание | recall | 10 |
| устаревший факт не всплыл | забывание, superseded | 5 |
| чужой проект | фильтры scope | 5 |
| запрос не про память | порог, право молчать | 5 |
| «ага», «продолжай» | режим profile | 3 |
| много релевантного | elbow отдаёт больше | 2 |

Отдельно проверить, что **количество выдачи меняется**. Если на всех 30
запросах вернулось одинаковое число фактов — гибкая выдача не работает,
elbow не срабатывает, и ты вернулся к фиксированному лимиту.

```python
counts = [len(search(c.query)) for c in cases]
assert len(set(counts)) > 5          # выдача действительно адаптивна
assert min(counts) == 0              # хоть где-то молчит
```

## Слой 4 — Долгий прогон

Единственный способ найти тихую деградацию. Ни один тест из слоёв 1–3 её не
видит.

Взять реальную историю Hermes (`reextract` из его SessionDB) или 300–500 ходов
синтетики, прогнать целиком, потом посмотреть на пять метрик.

```
1. Кривая роста фактов
   активных фактов на каждые 100 ходов
   → должна выходить на плато

2. Распределение по scope
   SELECT scope, COUNT(*) FROM memories WHERE status='active' GROUP BY 1
   → 95% в 'user' означает, что дрейф уже случился

3. Доля почти-дублей
   пары active-фактов одного type с cos > 0.92
   → выше 5% значит судья не мержит

4. Противоречия
   пары с cos > 0.85 → отдать судье вопрос «противоречат?»
   → считать количество

5. Источники
   SELECT source_role, COUNT(*) ... GROUP BY 1
   → фактов с source_role='assistant' должно быть 0
```

**Метрика №1 — самая дешёвая и самая показательная.** Если число активных
фактов растёт линейно с объёмом разговоров, система сломана, независимо от
того, что показывают остальные тесты. Здоровая память выходит на плато:
новые факты в основном обновляют старые, а не добавляются к ним.

Прогонять раз в месяц и после каждой смены промпта. Результаты складывать
в файл рядом с датой и версией промпта — через полгода это будет самое
полезное, что у тебя есть.

## Чего не делать

- **Не мокать судью в слое 2.** Ты тестируешь именно его поведение. Мокать
  можно в слое 1, где проверяется сантехника.
- **Не писать тесты на точные строки фактов.** Модель перефразирует; тест
  будет краснеть без причины и его отключат.
- **Не начинать с слоя 4.** Он самый интересный и самый бесполезный, пока
  слой 1 красный.
- **Не считать «оно отвечает» тестом.** Система, запоминающая чушь, отвечает
  ровно так же уверенно, как правильная.
